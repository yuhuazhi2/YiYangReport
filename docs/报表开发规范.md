# 报表开发规范（43 张表长期并行开发契约）

> 本文档是**框架与各报表之间的约定**。目的只有一个：
> 让你可以**每次只专心开发一张表**，且永远不必担心"改这张会不会弄坏之前做好的"。
>
> 每开发一张新表前，请先读一遍本文。它既是规范，也是排错清单。

---

## 一、最重要的三条铁律

### 铁律1：一张表 = 一个文件

| 要做的事 | 正确做法 | 禁止做法 |
|---|---|---|
| 新增 LK02 | 新建 `reports/lk02_profit.py` | 改 `registry.py` 加 import |
| 修改 LK01 取数 | 只改 `reports/lk01_sample.py` | 改 `base.py` / `registry.py` |

**原因**：框架已实现"自动扫描 `reports/lk*.py` + 逐个隔离加载"。
新增文件会被自动发现；某个文件写坏了，只会让它自己降级成占位报表，
**其他表照常工作**（已实测验证）。

> 文件命名必须以 `lk` 开头，如 `lk02_profit.py`、`lk12_1_ap_aging.py`。
> 框架靠这个前缀识别"这是报表实现"，不会误加载 base/stub/header 等框架文件。

### 铁律2：不修改框架层，只使用框架层

框架层文件（**不要为了某一张表去改它们**）：

```
core/excel_engine.py     Excel 读写能力
core/context.py          取数与缓存
core/db.py               数据库访问 + 只读防线
reports/base.py          报表基类
reports/registry.py      注册与加载
reports/header.py        通用页眉
verify/reconciliation.py 勾稽核对
```

**为什么**：这些文件被 43 张表共用。改动一处，可能同时影响全部报表。
如果确实需要新能力（例如某种特殊单元格操作），
**先把它加进框架层并做通用化**，再用到具体表上——不要在某张表里"就地打补丁"。

### 铁律3：取数一律走 ctx，不直接连库

```python
# 正确：自动享缓存 + 审计 + 自动带上目标年度库
rows = ctx.fetch(key, sql, params, report_code=self.code)

# 禁止：绕过缓存，且可能查错库
rows = self.ctx.db.query(sql, params)
```

**原因**：
- `ctx.fetch` 会把结果缓存起来，多个报表共用同一批数据时只查一次；
- 缓存键带库名，杜绝"2025 年报表填了 2026 年数据"这种灾难；
- 每次取数都会记入 `logs/sql_audit.log`，并用 `report_code` 标记归属，
  出问题时能按报表代码直接筛出相关 SQL。

## 三、写单元格：选对方法（关键）

框架提供了多个写入方法，**选错会导致数据显示异常**。这是最容易踩的坑。

| 方法 | 用途 | 典型场景 |
|---|---|---|
| `set(cell, value)` | 普通写入，Excel 自行判断类型 | 写数字（金额、数量） |
| `set_text(cell, text)` | **强制文本**，先设格式再写值 | 写年月、编号、带前导零的代码 |
| `set_rc(row, col, value)` | 按行列写（1-based） | 已知行列、写数字 |
| `set_text_rc(row, col, text)` | 按行列写文本 | 页眉文字 |
| `set_block(row, col, rows_2d)` | **二维块一次写完** | 明细表几十上百行 |
| `set_formula(cell, "=SUM(...)")` | 写公式 | 合计行、动态插行后重算 |

### 必须用 `set_text()` 的情形（踩过坑）

**任何"文字"只要包含数字，就有被 Excel 误判为日期/数值的风险。**

真实案例：LK01 的 C4 要求写"2026年5月"，用 `set()` 写入后，
Excel 把它当成日期 2026-05-01，内部存成序列号 **46143**，
而该格又是金额格式，最终显示成 **`46,143.00`** —— 看起来像一笔钱。

正确做法：

```python
hook.set_text("C4", "2026年5月")   # 先设文本格式 "@"，再写值
```

**顺序不能反**：必须先设格式、再写值。反过来值已变成 46143，
再改格式只会显示成 `46143`。

### 需要 `set_text()` 的常见情况

- 会计期间、年月（"2026年5月"）
- 可能以 0 开头的编码（"001"、"0123"）
- 纯数字编号但语义是文字（发票号、合同号）
- 任何"看起来像日期"的文字

## 四、定位单元格：优先按内容，而不是写死坐标

### 推荐：按内容定位

```python
# 找到"货币资金"所在行（列1）
row = hook.find_row("货币资金", col=1)
if row:
    hook.set_rc(row, 3, money)     # 第3列 = 期末余额
```

**好处**：
- 模板将来挪一行，代码不用改；
- 代码自解释，比 `set_rc(15, 3, ...)` 直观得多；
- 不会因为数错行而把数字写到别的项目上（这类错误极难发现）。

### 允许写死坐标的情形

- 页眉固定格（如 C4 写会计期间）——已由需求明确指定
- 结构极其规整、且已确认不会变动的表头
- 关键位置建议在代码里加注释说明"这是模板第几行第几列、内容是什么"

### 可用工具

```python
hook.find_row("关键字", col=1, start_row=1, max_row=0, exact=False)  # → 行号 或 0
hook.find_cell("关键字", start_row=1, max_row=0, max_col=0)          # → (行,列) 或 (0,0)
hook.used_range()                                                     # → (起行,起列,止行,止列)
```

> `find_cell` 找不到时返回 `(0, 0)` 而不是 `None`，方便直接解包后判 `r == 0`。

## 五、明细表：动态行处理（LK05/LK11/LK06 等必须掌握）

模板给明细表预留的行数是固定的（例如 LK05 预留 7 行），
但实际数据可能是 3 行，也可能是 60 行。**这是后期最容易出问题的地方**。

### 数据比预留多：插入行

```python
base_row = hook.find_row("库存原材料", col=1)   # 数据区首行
need = len(items)
have = 7                                        # 模板预留行数
if need > have:
    hook.insert_rows(base_row + have, need - have, copy_from=base_row)
```

**必须传 `copy_from`**：Excel 插入的空行不带边框、不带数字格式，
直接写数会"缺框线"，与模板风格不一致。传样板行号后，
框架会把该行的格式刷到新行上。

**注意**：插入后，原 `base_row` 之后的所有行（含合计行）都会**下移**。
所以合计行的公式必须重算：

```python
total_row = hook.find_row("合计", col=1)   # 插入后重新定位！不要用插入前的行号
hook.set_formula(f"C{total_row}", f"=SUM(C{base_row}:C{base_row + need - 1})")
```

### 数据比预留少：删除空行

```python
if need < have:
    hook.delete_rows(base_row + need, have - need)
```

> 也可以选择不删（保留空行，报表仍可用），但版面会显得松散。
> 建议：**先实现填数，版面美化放到该表功能验证通过之后再做**。
> 这样能把"逻辑错误"和"版面问题"分开排查。

### 一次写完，不要逐格写

```python
# 推荐：一次写完整块（快，尤其在局域网环境下）
hook.set_block(base_row, 1, [[序号, 名称, 数量, 金额], ...])

# 避免：几十上百行逐格 set_rc()，会发起成百上千次跨进程调用
```

## 六、特殊结构表（提前知道，不要临时改造框架）

已确认的三种特殊结构，框架能力**均已覆盖**，开发时不需要改框架：

### 1. LK21 横向月份表（49 列）

12 个月横向排列，每月 3 列（增加数/已交数/末欠数）。

```python
# 月份 → 列号 有规律可循，建议在报表类里写成一个映射
COL_OF_MONTH = {1: 3, 2: 6, 3: 9, ...}   # 具体值需对着模板确认
for month, col in COL_OF_MONTH.items():
    hook.set_rc(tax_row, col, amount)
```

### 2. LK11 分段小计表（28 个合并单元格）

结构为"一般客户（R12~R81）→ 小计 → 分期客户（R82~R101）→ 小计"。
不同分段的行范围不同，且中间有大量空白行。

```python
sec1 = hook.find_row("一般客户：", col=1)
sub1 = hook.find_row("一般客户小计", col=1)
sec2 = hook.find_row("分期客户：", col=1)
sub2 = hook.find_row("分期客户小计", col=1)
# 各段独立填数，小计行用 set_formula 或直接写计算值
```

### 3. LK06-1 超宽表（256 列）

列数极多但结构规整，按列号循环处理即可。
不要试图逐列手工列举，写成"分组 × 字段"的循环。

## 七、勾稽核对：登记 cell_map

每张表都应把**参与勾稽关系的关键指标**登记到 `cell_map`：

```python
cell_map = {
    "货币资金_期末": "C15",     # 指标名 → 单元格
    "应收账款_期末": "C18",
}
```

父类会自动在读回这些格子的值并登记到 `ctx`，
供 [`verify/reconciliation.py`](../verify/reconciliation.py) 使用。

### 注意

- **只登记确实写了数值的格子**。
  曾出现 `cell_map` 指向表头文字格"期末余额"，导致核对时
  `float("期末余额")` 报错，整份核对报告丢失。
- 核对模块现在已加固：非数值指标会被判为"无法核对"，不再崩溃。
  但这属于兜底，**不应依赖它**——登记错误本身要修。

## 八、容错与降级（框架已提供，务必理解）

| 情形 | 框架行为 | 对用户的影响 |
|---|---|---|
| 某报表模块语法/导入错误 | 该模块跳过，记入 `load_failures()` | 该表退化为占位页，其他表正常 |
| 某张表 `fetch()`/`write()` 抛异常 | 记入 `result.failed`，继续下一张 | 该表无数据，其他表正常 |
| 数据库连不上 | 生成"骨架报表"（表页复制、不填数） | 可验证版式，无数据 |
| 账套号/年度解析不出 | **整体停止，不产出文件** | 宁可不出表，也不出错表 |
| 勾稽核对遇到非数值 | 判为"无法核对"，不中断 | 核对报告正常产出 |

**设计原则**：单点故障不扩散；但"数据源定位"这类根本性错误必须立即停止。

## 九、提交前自检清单

每完成一张表，请逐条确认：

- [ ] 新增的是**独立文件** `reports/lkXX_xxx.py`，没有改框架文件
- [ ] 类上加了 `@register`，`code` 与模板中的表页代码完全一致
- [ ] `fetch()` 全部通过 `ctx.fetch(...)` 取数，并带 `report_code=self.code`
- [ ] 文字类单元格用了 `set_text()` / `set_text_rc()`
- [ ] 定位优先用 `find_row()` / `find_cell()`，写死坐标处有注释说明
- [ ] 明细表处理了"数据多于/少于预留行"两种情况
- [ ] 动态插行后，合计公式已按**新行号**重算
- [ ] `cell_map` 只包含确实写了数值的格子
- [ ] 单独生成这张表验证过：数字与用友前台/后台一致
- [ ] 顺带生成一张**之前已完成的表**，确认它没有受到影响

## 十、遇到框架能力不足时怎么办

这是长期项目必然遇到的情况。**处理原则：向上扩展，不就地打补丁。**

```text
❌ 错误做法
   在 lk20_xxx.py 里直接用 self.hook.ws.Range(...).SomeExcelApi()
   → 这张表用了框架没封装的能力，别人维护时看不懂，
     将来 Excel 版本变化也无从统一处理。

✅ 正确做法
   1. 判断这个能力是否"其他表也可能用到"
   2. 若会用到 → 加到 core/excel_engine.py 的 _SheetHook 里，
      写清文档与用法示例
   3. 若只此一张表用 → 也加到框架层，但注明"仅供 LK20 使用"
   4. 然后所有表统一通过 hook 调用
```

**为什么值得这样做**：43 张表意味着会有 43 次"遇到新情况"的机会。
每次都往框架里加一个通用能力，框架会越来越强；
每次都就地打补丁，框架会逐渐被架空，最后无人能维护。

## 十一、当前框架能力一览（截至本版）

### `_SheetHook` 已提供

| 类别 | 方法 |
|---|---|
| 写值 | `set` `set_rc` `set_many` `set_row` |
| 写文本 | `set_text` `set_text_rc` |
| 批量写 | `set_block` |
| 写公式 | `set_formula` |
| 读值 | `get` `get_rc` `get_block` |
| 定位 | `find_row` `find_cell` |
| 动态行 | `insert_rows` `delete_rows` |
| 合并 | `merge` `unmerge` |
| 格式 | `set_number_format` |
| 边界 | `used_range` `used_rows` `used_cols` `name` |

### 注册与加载

| 能力 | 说明 |
|---|---|
| 自动发现 | 扫描 `reports/lk*.py`，无需改 registry |
| 隔离加载 | 单模块失败不影响其他模块 |
| 失败查询 | `registry.load_failures()` |
| 已实现清单 | `registry.implemented_codes()` |

### 取数与核对

| 能力 | 说明 |
|---|---|
| 缓存取数 | `ctx.fetch` / `ctx.fetch_dict` |
| 指标登记 | `ctx.register_report_data` |
| 勾稽核对 | `Reconciler(ctx).report_text()`，三态（通过/不符/无法核对） |
| SQL 审计 | 自动写入 `logs/sql_audit.log`，带报表代码标记 |

## 十二、记住一句话

> **框架负责"所有表都要做的事"，报表文件只负责"这张表特有的逻辑"。**

只要守住这条边界，43 张表可以一张一张、互不干扰地做完；
哪天某张表需要返工，也只动它自己的文件，其他表安然无恙。
